### Retry (em `webapi_provider.py:_do_request()`)

```
Política:
- Apenas requisições GET são retentadas (attempts = max_retries + 1)
- Backoff: min(2^(attempt-1), 5) * uniform(0.5, 1.5) segundos
- Exceções retryable: PiTimeoutError, PiSSLError, PiUnavailableError, PiRateLimitedError
- Durante sleep: semáforo global é liberado → sleep → semáforo re-adquirido
- Non-GET: executa exatamente 1 vez
```

### Risco de N+1 queries

**Baixo para carga.** As relações usam `lazy="joined"`, então **uma única query** com quatro JOINs retorna as 24 `CepVariable` e suas `PiTag` associadas. Não são consultas separadas — são JOINs dentro de uma única query ORM.

## 5. Estratégias de Consulta Encontradas

### 5.1 Consulta simples (PiService)

```
Para cada tag individualmente:
  1. _ensure_web_id(tag)  → resolve WebId (cache → PI → DB)
  2. provider.get_recorded_values() ou provider.get_interpolated_values()
  3. Retorna PiValue[] com timestamp, value, quality flags
```

- **Uso**: Consultas com poucas tags ou debug
- **Limitação**: Sem chunking, sem sampling, sem StreamSet

### 5.2 Consulta avançada (PiLongRangeService)

```
1. build_plan_for_visual() → chunking temporal
2. _resolve_web_ids() → cache WebId (single-flight, 24h)
3. VisualCache peek → hit? retorna; miss? busca
4. Recorded: fetch_recorded_streamsets_batch() → Batch POST → splitting
5. Interpolated: fetch_streamset_batch() → StreamSet → fallback individual
6. Sampling: LTTB para numéricos
7. Armazena no VisualCache
```

- **Uso**: Endpoints de visualização com resolução automática
- **Vantagem**: Chunking adaptativo, sampling, cache

### 5.3 StreamSet (interpolated)

```
GET /streamsets/interpolated?webId=W1&webId=W2&...&startTime=...&endTime=...&interval=...
```

- Função real: `fetch_streamset_batch()` em `streamset_client.py:398`
- Lotes de `pi_query_streamset_batch_size` (default 10)
- Fallback individual em caso de 400/404/405/501
- Recovery com janelas de 30 dias para séries falhas

### 5.4 Batch (recorded)

```
POST /batch
{
  "key1": {"Method": "GET", "Resource": "https://.../streamsets/recorded?webId=W1&..."},
  "key2": {"Method": "GET", "Resource": "https://.../streamsets/recorded?webId=W2&..."}
}
```

- Função real: `fetch_recorded_streamsets_batch()` em `streamset_client.py:708`
- Wave-based processing
- Window splitting para períodos longos
- Retry em 429 com backoff
- Fallback para endpoints individuais em 400/404/405/501

### 5.5 Consulta individual (fallback)

- Função real: `provider.get_interpolated_values()` / `provider.get_recorded_values()`
- Usada **apenas** como fallback quando lotes falham (comportamento existente em `streamset_client.py`)
- **Não é o caminho principal** para o CEP

## 6. Comparação: Batch vs StreamSet vs Streams Individuais

### Tabela comparativa

| Critério | StreamSet Interpolated | Batch Recorded | Streams Individuais |
|---|---|---|---|
| **Endpoint** | `GET /streamsets/interpolated` | `POST /batch` (contém `GET /streamsets/recorded`) | `GET /streams/{webId}/recorded` ou `/interpolated` |
| **Requisições para 73 tags** | ceil(73/10) = 8 GETs | 8 grupos internos (pi_streamset_recorded_max_webids=10) → subrequisições Batch agrupadas conforme pi_batch_max_requests; POSTs HTTP efetivos dependem desse limite e do window splitting — ver nota abaixo | 73 GETs |
| **Alinhamento temporal** | Automático (intervalo fixo) | Por ponto gravado (timestamps reais) | Manual (por tag) |
| **Precisão dos dados** | Interpolado (depende do intervalo) | Gravado (dados reais) | Gravado (dados reais) |
| **Chunking** | Não nativo | Sim (window splitting adaptativo) | Não |
| **Deduplicação** | Automática no parse | Automática no merge de chunks | Não |
| **Fallback** | Sim → individual em 400/404/405/501 | Sim → individual em 400/404/405/501 | N/A |
| **Retry** | Via `_global_semaphore` + `_do_request()` | Via `_BATCH_SEMAPHORE` + retry 429 | Via `_global_semaphore` + `_do_request()` |
| **Concorrência** | Semáforo global (4) | Batch semaphore (2) + semáforo global | Semáforo global (4) |
| **Recovery** | Janelas de 30 dias para séries falhas | Window splitting + retry 429 | Não aplicável |
| **Sampling/LTTB** | Disponível via `_sample_series()` | Disponível via `_sample_series()` | Disponível via `_sample_series()` |
| **VisualCache** | Disponível para queries de visualização | Disponível para queries de visualização | Disponível para queries de visualização |
| **Complexidade de uso** | Média | Alta (wave processing) | Baixa |
| **Função real** | `fetch_streamset_batch()` em `streamset_client.py` | `fetch_recorded_streamsets_batch()` em `streamset_client.py` | `provider.get_interpolated_values()` / `provider.get_recorded_values()` |

**Nota sobre Batch Recorded — distinção entre grupos, subrequisições e HTTP efetivas:**
- **Grupos internos:** 73 WebIds ÷ `pi_streamset_recorded_max_webids` (10) = 8 grupos. Cada grupo gera uma Resource URL (`GET /streamsets/recorded?webId=W1&...&webId=W10`).
- **Subrequisições do Batch:** cada grupo vira uma entrada no envelope `POST /batch` (até `pi_batch_max_requests` por POST).
- **POSTs HTTP efetivos:** com `pi_batch_max_requests=10`, os 8 grupos cabem em 1 único POST /batch. Se window splitting subdivide grupos (períodos longos), o número de Resources e POSTs pode aumentar. A quantidade real depende da implementação e do período consultado.

### Estratégia híbrida para CEP

O fluxo CEP usa **duas modalidades** simultaneamente:

**Interpolated 5m — entrada exclusiva do calculador CEP:**
- Grade temporal comum para os pontos efetivamente retornados (timestamps idênticos entre leitura, limites e alvo quando todas as séries obrigatórias retornam o mesmo instante)
- `calculate_compliance()` faz lookup por timestamp idêntico
- Intervalo fixo de 5 minutos (não configurável pelo usuário)
- Não exposto no contrato público (`interval` não é parâmetro de endpoint CEP)

**Recorded — consulta separada, preservado internamente:**
- Consulta via `fetch_recorded_streamsets_batch()` em `streamset_client.py`
- Dados reais gravados no PI Data Archive
- Convertido pelo CepPiAdapter quando necessário, mas nunca alimenta `calculate_compliance()`
- Preservado internamente pela orquestração; exposição HTTP (inline, separada, paginada ou omitida) permanece pendente em D7
- Útil para: histórico para gráfico, períodos curtos, transições específicas

**Fluxo principal (lotes):**
```
1. Carregar as 24 configurações CEP do banco
2. Reunir e deduplicar exatamente 73 tags funcionais únicas
3. Solicitar ao serviço de resolução a resolução dos WebIds
   (o serviço reutiliza WebIdCache e aplica a persistência existente)
4. Solicitar ao streamset_client.py a aquisição das séries em lotes
5. Consultar Interpolated 5m em lote via fetch_streamset_batch()
6. Consultar Recorded separadamente em lote via fetch_recorded_streamsets_batch()
7. Converter PiValue para CepSample via CepPiAdapter
8. Enviar somente Interpolated 5m ao calculate_compliance
9. Preservar Recorded internamente
10. Agregar resultados internos e diagnósticos
```

**Restrições de lote:**
- `pi_query_streamset_batch_size` (default 10) controla tags por lote StreamSet
- `pi_streamset_recorded_max_webids` (default 10) controla WebIds por grupo recorded
- `pi_batch_max_requests` (default 10) controla requests por POST batch
- **Não aumentar** `pi_query_max_tags` — o limite de configurações não é o limite de tags por lote

**O que NÃO usar no caminho CEP:**
- **VisualCache**: não será utilizado na primeira implementação CEP
- **LTTB/downsampling**: nenhum dado submetido a redução de pontos alimentará o calculador
- **Cache de séries CEP**: não será criado cache específico para séries CEP
- **Consultas individuais por tag**: usadas apenas como fallback quando o lote falha
- **Nenhuma camada adicional de retry**: o retry já existente no `webapi_provider.py:_do_request()` é suficiente

**Quando Recorded é útil (fora do cálculo):**
- Exibição de valores reais no frontend
- Auditoria de limites que mudaram durante o período
- Diagnóstico de transições específicas

## 7. Comparação: Recorded vs Interpolated

### Tabela comparativa

| Aspecto | Recorded | Interpolated |
|---|---|---|
| **Fonte** | Valores gravados no PI Data Archive | Interpolação linear entre pontos gravados |
| **Timestamps** | Reais (podem ter gaps e irregularidades) | Regulares (intervalo fixo definido) |
| **Alinhamento entre séries** | Cada série pode ter timestamps diferentes | Nos pontos efetivamente retornados por todas as séries obrigatórias, os timestamps coincidem |
| **Limites que mudam** | Cada ponto reflete o limite exato no momento | Interpolação pode suavizar transições de limite |
| **Dados ausentes** | Não gera pontos onde não existem dados | Gera pontos interpolados mesmo entre dados reais |
| **Chunking** | Window splitting adaptativo | Chunking por duração (chunk_max_points × interval_seconds) |
| **Lotes** | Batch POST com wave processing | StreamSet GET com batch_size |

### Papel de cada modalidade no fluxo CEP

**Interpolated 5m** é a **entrada exclusiva** do calculador CEP:
- Fornece uma grade temporal comum para os pontos efetivamente retornados
- Isso elimina o desalhamento como causa de SEM_DADOS somente quando todas as séries obrigatórias retornam pontos válidos nos timestamps esperados
- `calculate_compliance()` recebe `CepSample[]` derivados do interpolated
- Ainda pode haver SEM_DADOS quando:
  - uma série obrigatória não retorna o timestamp esperado
  - um valor obrigatório está ausente ou inválido
  - a qualidade é ruim conforme as regras da F7.3
  - ocorre falha de resolução ou integração
  - um limite obrigatório não está disponível
- Não cria timestamps artificiais quando a série de leitura está completamente ausente

**Recorded** é consultado **separadamente**, convertido quando necessário e **preservado internamente** pela orquestração. Ele nunca alimenta `calculate_compliance()`.
- Dados reais gravados no PI Data Archive
- **Não alimenta** `calculate_compliance()`
- A D7 ainda decidirá se Recorded será exposto ou não pelo futuro endpoint; se será retornado inline, em campo separado, paginado, ou disponibilizado por outro recurso
- Permite verificar se limites mudaram durante o período (comparando com interpolated)

### Consequência para o alinhamento exato do calculador

O calculador da F7.3 (`calculate_compliance()`) usa **alinhamento exato por timestamp**:

```python
# No calculador (cep_calculator.py):
reading_map = {r.timestamp: r for r in reading_recovered}
lower_map = {t.timestamp: t for t in lower_recovered}

for r_sample in reading_sorted:
    ts = r_sample.timestamp
    lo_rec = lower_map.get(ts)  # ← busca EXATA por timestamp
    # Se não existe → lo_eff = None → SEM_DADOS
```

**Com Interpolated 5min:**
- Leitura: T1, T2, T3, T4, T5, ... (a cada 5min)
- Limite inferior: T1, T2, T3, T4, T5, ... (a cada 5min)
- Interpolated 5m estabelece uma grade temporal comum para os pontos efetivamente retornados
- Ainda pode haver SEM_DADOS quando: uma série obrigatória não retorna o timestamp esperado; o valor está ausente ou inválido; a qualidade PI é ruim conforme F7.3; ocorre falha de resolução ou integração; um limite obrigatório não está disponível

**Com Recorded (apenas para referência — não alimenta calculador):**
- Leitura pode ter timestamps: T1, T2, T3, T5, T8 (irregulares)
- Limite inferior pode ter: T1, T3, T5, T7 (diferentes)
- Se alimentasse o calculador: T2, T7, T8 ficariam SEM_DADOS para lower
- Mas Recorded não alimenta o calculador — é preservado internamente

### Decisão registrada

**Para cálculo de conformidade: Interpolated 5 minutos (intervalo fixo, não configurável).**

Justificativa:
- O calculador exige alinhamento exato por timestamp
- Interpolated 5m estabelece uma grade temporal comum para os pontos efetivamente retornados
- Granularidade de 5min é suficiente para detectar violações de limites industriais

**Recorded:** consultado separadamente, convertido pelo adaptador quando necessário, preservado internamente pela orquestração, nunca alimenta o cálculo. A representação HTTP definitiva dessa informação permanece pendente na D7.

## 8. Mapeamento de Qualidade e Timestamps

### Pipeline completo: PI → CepSample

```
fetch_streamset_batch() em lotes
  │
  ├─ Resposta HTTP JSON
  │   └─ _parse_values(payload) → walk recursivo → PiValue[]
  │       ├─ Timestamp: _normalize_timestamp() → datetime UTC-aware
  │       ├─ Value: _normalize_value() → int/float/str/bool/dict/None
  │       ├─ Good: _normalize_boolean() → bool
  │       ├─ Questionable: _normalize_boolean() → bool
  │       └─ Substituted: _normalize_boolean() → bool
  │
  └─ CepPiAdapter (futuro)
      └─ _pi_value_to_cep_sample(pi_value) → CepSample
          ├─ value: verificar tipo em ordem:
          │    1. isinstance(v, bool) → valor_não_numerico (rejeitar)
          │    2. isinstance(v, (int, float)) and math.isfinite(v) → float(v)
          │    3. None → None
          │    4. Qualquer outro → None (valor_não_numerico)
          ├─ quality: PointQuality(good, questionable, substituted)
          └─ timestamp: pi_value.timestamp (já UTC-aware)
```

### Tabela de conversão de valores

| Tipo no PiValue | Exemplo | `_normalize_value()` | `_pi_value_to_cep_sample()` | No calculador |
|---|---|---|---|---|
| `float` finito | `42.5` | `42.5` | `CepSample(ts, 42.5, Q)` | `value=42.5` |
| `int` finito | `42` | `42` | `CepSample(ts, 42.0, Q)` | `value=42.0` |
| `None` | `None` | `None` | `CepSample(ts, None, Q)` | bad value → SEM_DADOS |
| `float("nan")` | `NaN` | `float("nan")` | `CepSample(ts, None, Q)` | valor ausente → SEM_DADOS |
| `float("inf")` | `Inf` | `float("inf")` | `CepSample(ts, None, Q)` | valor ausente → SEM_DADOS |
| `-999.0` | `-999` | `-999.0` | `CepSample(ts, -999.0, Q)` | preservado → calculador rejeita |
| `str` | `"ABC"` | `"ABC"` | `CepSample(ts, None, Q)` | valor ausente → SEM_DADOS |
| `dict` (digital) | `{"Name":"Shutdown"}` | `"Shutdown"` | `CepSample(ts, None, Q)` | valor ausente → SEM_DADOS |
| `bool` | `True` | `True` | **Rejeitado** (não é número) | valor_não_numerico |

### Regras de conversão numérica

O adaptador deve:
- Rejeitar `bool` explicitamente (Python: `bool` é subclasse de `int`)
- Aceitar apenas `int` e `float` finitos
- Rejeitar `None`, `NaN`, `+inf`, `-inf` → valor ausente
- Preservar `-999` para o calculador aplicar sua regra existente
- Rejeitar texto e PI digital states sem conversão silenciosa
- Não confundir erro HTTP com valor PI ruim
- Não calcular média dos vizinhos (responsabilidade do calculador)

### Mapeamento de Quality Flags

| Campo PI | PiValue field | PointQuality field | CepCalculatedPoint field |
|---|---|---|---|
| Good | `PiValue.good` | `PointQuality.good` | → `_is_bad_value()` decide se é bad |
| Questionable | `PiValue.questionable` | `PointQuality.questionable` | → `_is_bad_value()`: se True → bad |
| Substituted | `PiValue.substituted` | `PointQuality.substituted` | → `*_source_substituted` (preservado, não afeta conformidade) |

### Tratamento de `-999`

O PI AF usa `-999` como sentinel para "sem dado". O provider o preserva como `-999.0`. O calculador (`_is_bad_value()`) o rejeita:

```python
# Em cep_calculator.py:
def _is_bad_value(value, quality):
    ...
    if value == -999.0:
        return True, "value is -999"
    ...
```

Resultado: pontos com `-999` são tratados como bad → imputação por média de vizinhos → ou SEM_DADOS se não houver vizinhos.

### Preservação de source_substituted

O flag `substituted` do PI indica que o valor foi interpolado/cálculo pelo PI (não é leitura direta). O fluxo completo:

```
PiValue.substituted = True
  → PointQuality.substituted = True
  → RecoveredValue.source_substituted = True
  → CepCalculatedPoint.reading_source_substituted = True (ou lower/upper/target)
```

O valor é usado normalmente no cálculo, mas o flag é preservado para transparência. **Não confundir** com `imputed` (recuperação local por média de vizinhos).

### Diagnósticos e distinção de falhas

O fluxo CEP deve diferenciar explicitamente cada situação. Erros de integração **não podem ser indistinguíveis** de séries válidas vazias:

| Situação | Tipo | Representação | Efeito no CEP |
|---|---|---|---|
| Consulta válida sem pontos | Série vazia válida | `CepSample[]` vazio | Sem dados para classificar |
| Tag inexistente no PI (resolução falha) | Erro de resolução | `PiTagNotFoundError` via `resolve_point()` (404) → WebIdCache invalida a entrada; tag marcada INVALID no DB | Falha da série com diagnóstico de resolução — distinguível de série vazia válida |
| WebId previamente resolvido rejeitado pelo PI durante consulta de dados | Erro de consulta | WebId existe no cache/DB mas PI rejeita na request de dados; **lacuna**: não existe mecanismo automático de invalidação no caminho CEP — comportamento futuro necessário | Diagnóstico a ser definido; resultado ainda não determinado |
| Timeout na requisição | Erro de integração | `PiTimeoutError` (retryable) → diagnosticado | Retry → se falhar, falha da série com diagnóstico — distinguível de série vazia válida |
| Auth falhou no PI | Erro de integração | `PiAuthError` (não retryable) → diagnosticado | Falha da série com diagnóstico — distinguível de série vazia válida |
| PI indisponível (conexão recusada/erro de conexão) | Erro de integração | `PiUnavailableError` (retryable) → diagnosticado | Retry → se falhar, falha da série com diagnóstico — distinguível de série vazia válida |
| Resposta malformada | Erro explícito | `PiInvalidResponseError` → diagnosticado | Falha da série com diagnóstico — distinguível de série vazia válida |
| Valor Good=False | Valor PI ruim | `CepSample(value=..., quality.good=False)` | Calculador trata como bad → SEM_DADOS |
| Valor = -999 | Valor PI ruim | `CepSample(value=-999.0, quality.good=True)` | Calculador rejeita → SEM_DADOS |
| Digital state | Valor PI ruim | `CepSample(value=None, quality.good=True)` | Calculador trata como bad → SEM_DADOS |

**Na falha parcial por variável:**
- Processar configurações recuperáveis
- Retornar diagnóstico por tag e por configuração
- Limite obrigatório indisponível torna os pontos afetados SEM_DADOS
- Alvo ausente não invalida a conformidade
- Leitura completamente ausente não cria timestamps
- Leitura ausente retorna coleção vazia com diagnóstico (distinguir de falha de integração)
- Erro de integração não pode ser indistinguível de série válida vazia

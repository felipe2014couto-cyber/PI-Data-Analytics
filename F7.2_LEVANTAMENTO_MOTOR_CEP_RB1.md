## 4. Fluxo Atual de Consulta ao PI Web API

### 4.1 Consulta Simples (`GET /time-series` sem `resolution_mode`)

```
1. API recebe tag_ids, start_time, end_time, mode
2. PiService.fetch_time_series()
   a. Valida período
   b. Carrega PiTags do banco
   c. Para cada tag:
      - _ensure_web_id(): resolve WebId (cache DB → PI → grava no DB)
      - get_recorded_values() ou get_interpolated_values()
      - Constrói TimeSeriesSeries com equipment/section/variable_type
   d. Coleta erros por tag
3. Retorna TimeSeries{series[], errors[]}
```

### 4.2 Consulta Avançada (`GET /time-series` com `resolution_mode`)

```
1. API registra query_id no QueryRegistry
2. PiLongRangeService.fetch_time_series()
   a. build_plan_for_visual(): chunking temporal
   b. _resolve_web_ids(): cache WebId (single-flight, 24h)
   c. VisualCache: peek → hit? retorna; miss? busca
   d. Recorded: fetch_recorded_streamsets_batch() → Batch POST → splitting
   e. Interpolated: fetch_streamset_batch() → StreamSet → fallback individual
   f. Sampling: LTTB para numéricos
   g. Armazena no VisualCache
3. Retorna TimeSeries com QueryExecutionMetadata
```

### 4.3 Fluxo de WebId Resolution

```
Tag sem WebId
  → _ensure_web_id(tag)
    → tag.pi_web_id existe? retorna
    → WebIdCache.peek() → hit? usa
    → provider.resolve_point(path) → GET /points?path=\\SERVER\TAG
      → Sucesso: grava no DB + cache
      → PiTagNotFoundError: mark INVALID, invalidate cache
      → Outro erro: mark ERROR, invalidate cache, re-raise
```

## 5. Como as 73 Referências Estão Relacionadas Hoje

### 5.1 Estrutura Atual

As 73 tags PI da RB1 foram cadastradas via `scripts/seed.py` com o manifesto `_RB1_TAGS`. Cada tag é uma linha na tabela `pi_tags` com:

| Coluna | Conteúdo | Exemplo |
|---|---|---|
| `equipment_id` | FK para `equipments` (RB1) | 2 |
| `section_id` | FK para `sections` (DECAPAGEM_ELETROLITICA, etc.) | 7 |
| `variable_type_id` | FK para `variable_types` (CURRENT, TEMPERATURE, etc.) | 5 |
| `pi_tag_name` | Nome técnico da tag PI | `LFI_RB1_COR_ESC1` |
| `description` | **Papel da tag** ("Leitura", "Limite inferior", "Limite superior", "Valor objetivo") | "Leitura" |
| `display_name` | Nome amigável | "Escova 01" |

### 5.2 Agrupamento por Variável

As 24 variáveis são agrupadas implicitamente por **equipamento + seção + tipo de variável + display_name base**. Por exemplo, a variável "Escova 01":

```
PiTag(equipment=RB1, section=DECAPAGEM_ELETROLITICA, type=CURRENT, description="Leitura",     tag=LFI_RB1_COR_ESC1)
PiTag(equipment=RB1, section=DECAPAGEM_ELETROLITICA, type=CURRENT, description="Limite inferior", tag=LFI_RB1_DECAPAGEM_ELETROLITICA_COR_ESCOVA01_LIM_INF)
PiTag(equipment=RB1, section=DECAPAGEM_ELETROLITICA, type=CURRENT, description="Limite superior", tag=LFI_RB1_DECAPAGEM_ELETROLITICA_COR_ESCOVA01_LIM_SUP)
```

### 5.3 Respostas às Perguntas Críticas

**Existe um relacionamento persistido entre essas tags?**
Não explicitamente. As tags são relacionadas implicitamente por compartilhar `equipment_id`, `section_id`, `variable_type_id` e ter um `description` que indica o papel. Não há uma tabela "variável monitorada" ou "grupo de medição".

**O papel está em uma coluna estruturada ou em texto/código?**
Em texto livre: o campo `description` da tabela `pi_tags` armazena `"Leitura"`, `"Limite inferior"`, `"Limite superior"` ou `"Valor objetivo"`. Isso é validado apenas no seed Python, não por constraint no banco.

**Existe uma entidade correspondente à variável monitorada?**
Não. Não existe tabela `monitored_variables` ou `measurement_groups`. A "variável" é um conceito implícito no seed.

**A associação depende do manifesto Python do seed?**
Sim. A lógica de agrupamento (quais tags formam a variável "Escova 01") existe apenas no dicionário `_RB1_TAGS` em `seed.py`. No banco, a唯一 forma de reconstruir o grupo é consultando tags com o mesmo equipamento/seção/tipo e derivando o nome base do `display_name`.

**Seria seguro alterar o nome ou descrição de uma tag?**
Não. Alterar `display_name` ou `description` de uma tag quebraria a lógica de agrupamento baseada em string. Por exemplo, renomear "Escova 01 - Limite Inferior" para qualquer outra coisa tornaria impossível reconstruir o grupo "Escova 01" sem conhecimento prévio.

**Há constraints que impeçam relacionamentos duplicados?**
A constraint `uq_pi_tags_server_tag` impede duplicatas de `(pi_server, pi_tag_name)`. Não há constraint sobre o número de tags "Leitura" por variável.

**Como diferenciar variáveis de mesmo nome em seções diferentes?**
Pela combinação `section_id` + `display_name` (ou `variable_type_id`). No manifesto atual, cada variável é única dentro de sua seção.

## 6. Lacunas do Modelo Atual

### 6.1 Ausência de Entidade "Variável Monitorada"

O modelo atual não possui uma entidade que represente a variável CEP como um todo. As 4 tags (leitura, lim.inf, lim.sup, alvo) são independentes. Para o motor CEP, é essencial saber quais tags formam um conjunto de medição.

**Solução necessária:** Criar uma tabela `cep_variables` (ou similar) que agrupe as tags por variável monitorada, com campos como:
- `equipment_id`, `section_id`, `variable_type_id`
- `reading_tag_id` (FK → pi_tags)
- `lower_limit_tag_id` (FK → pi_tags, nullable)
- `upper_limit_tag_id` (FK → pi_tags, nullable)
- `target_tag_id` (FK → pi_tags, nullable)
- `code`, `name`, `active`

### 6.2 Ausência de Lógica de Conformidade

Não existe código que compare leituras com limites. O PI AF já faz isso (via `PerformanceEquation` → tags `_ONLINE`), mas o motor CEP precisa replicar essa lógica no banco local.

### 6.3 Ausência de Persistência de Resultados CEP

Não há tabelas para armazenar:
- Resultados de conformidade (por período)
- Percentuais de conformidade
- Períodos fora dos limites
- Execuções de análise

### 6.4 Campo `description` Sobrecarregado

O campo `description` do `PiTag` é usado como "papel da tag" (Leitura/Limite/Alvo), não como descrição humana. Isso cria acoplamento semântico frágil.

## 7. Estratégia de Consulta Recomendada

### 7.1 Para "Valor Atual" (Dashboard)

**Recomendação:** Consultar as 73 tags via StreamSet interpolated com intervalo de 1 minuto, última hora.

- Usar `fetch_streamset_batch()` existente
- 73 tags / batch_size=10 = 8 chamadas StreamSet
- Cache visual com TTL 15s para dados recentes
- Alternativa: consultar apenas as 24 tags de leitura + 24 de limite inferior + 24 de limite superior + 1 alvo = 73 tags

### 7.2 Para "Histórico para Gráfico"

**Recomendação:** Consultar as 24 tags de leitura via recorded com chunking adaptativo.

- Usar `fetch_recorded_streamsets_batch()` existente
- 24 tags / batch_size=10 = 3 chamadas
- Chunking automático para períodos longos
- Sampling LTTB para reduzir pontos

### 7.3 Para "Cálculo de Percentual de Conformidade"

**Recomendação:** Consultar recorded para leitura + limites, alinhar temporalmente, calcular em Python.

```
Para cada variável (24):
  1. Buscar recorded da tag de leitura (24 pontos/série)
  2. Buscar recorded do limite inferior (24 pontos/série)
  3. Buscar recorded do limite superior (24 pontos/série)
  4. Alinhar por timestamp (usar o timestamp da leitura)
  5. Para cada ponto: lower <= reading <= upper → CONFORME
  6. Calcular % = conformes / total * 100
```

**Estratégia de alinhamento temporal:**
- Usar o timestamp da leitura como referência
- Para cada timestamp de leitura, buscar o limite inferior e superior mais próximos (ou anterior igual)
- Se limites não existirem para o timestamp → SEM_DADOS
- Se leitura não existir → pular

**Ou alternativamente:** Usar interpolated com intervalo fixo (ex: 5min) para alinhar automaticamente todos os sinais.

### 7.4 Para "Identificação de Períodos Fora dos Limites"

**Recomendação:** Usar recorded com resolução fina (1min) e detectar transições de conformidade.

```python
#伪代码
for each timestamp:
    status = classify(reading, lower, upper)
    if status != previous_status:
        start_new_period(timestamp, status)
```

### 7.5 Consulta Recomendada — Resumo

| Caso de Uso | Modo | Tags | Estratégia | Reutiliza |
|---|---|---|---|---|
| Valor atual | interpolated | 73 | StreamSet batch | Sim |
| Gráfico histórico | recorded | 24 (leitura) | StreamSet batch + chunking | Sim |
| % conformidade | recorded | 73 | StreamSet batch + alinhamento Python | Sim |
| Períodos fora | recorded | 73 | StreamSet batch + detecção de transição | Sim |

**Não escolher intervalo de interpolação agora** — é decisão funcional pendente. Para o cálculo de conformidade, recorded é mais preciso (sem interpolação artificial).

### 8.3 Por Que Não Adicionar Campos ao Cadastro Atual

Adicionar `reading_tag_id`, `lower_limit_tag_id`, etc. ao model `PiTag` violaria o princípio de responsabilidade. O `PiTag` representa uma tag individual, não um grupo de medição. Criar uma tabela separada:
- Mantém o PiTag genérico e reutilizável
- Permite que uma tag pertença a múltiplas variáveis CEP (futuro)
- Não quebra migrations existentes
- Facilita filtros e relatórios CEP

### 8.4 Por Que Não Manter Apenas em Código

Manter o relacionamento apenas no manifesto Python:
- Impossibilita consultas SQL diretas
- Não permite CRUD via API
- Não permite que usuários configurem variáveis
- Fragiliza a manutenção

### 8.5 Impacto de Migration

- Nova migration: `0005_cep_variables_and_results`
- 4 novas tabelas
- FKs para tabelas existentes (equipments, sections, variable_types, pi_tags)
- Sem alteração em tabelas existentes
- SQLite compatível via `render_as_batch=True`

## 10. Estratégia de Cálculo

### 10.1 Regras de Conformidade

Baseado no `PerformanceEquation` do PI AF (extraído do `RB1.xml`):

```
Variável X:
  Leitura = tag Leitura
  LimInf  = tag Limite inferior
  LimSup  = tag Limite superior

  Se LimInf = -999 ou LimSup = -999:
    → SEM_DADOS

  Se LimInf <= Leitura <= LimSup:
    → CONFORME

  Se Leitura > LimSup:
    → FORA_LIMITE_SUPERIOR

  Se Leitura < LimInf:
    → FORA_LIMITE_INFERIOR

  Caso contrário:
    → SEM_DADOS
```

O valor-alvo (tag "Valor objetivo") é **informativo** e não altera a conformidade.

### 10.2 Tratamento de Edge Cases

| Edge Case | Tratamento Candidato | Decisão Necessária? |
|---|---|---|
| Limite inferior > limite superior | SEM_DADOS + log warning | Sim — validar no cadastro? |
| Leitura ausente (None/null) | SEM_DADOS | Não |
| Limite ausente (None/null) | SEM_DADOS | Não |
| Qualidade `Good=False` | SEM_DADOS | Sim — tratar Questionable como quê? |
| Qualidade `Substituted=True` | Usar o valor mas marcar | Sim — incluir ou excluir? |
| Valor não numérico (string) | SEM_DADOS | Não |
| NaN ou infinito | SEM_DADOS | Não |
| Timestamps diferentes (leitura vs limites) | Usar timestamp da leitura, buscar limite mais próximo | Sim — tolerância máxima? |
| Duplicidade de timestamps | Usar o último | Não |
| Dados fora de ordem | Ordenar por timestamp | Não |
| Mudança de unidade | SEM_DADOS (incompatível) | Não |
| Timezone | Tudo convertido para UTC pelo provider | Não |
| Início/fim do período | Usar `boundaryType=Inside` (recorded) | Não |
| Arredondamento | Precisão float padrão (IEEE 754) | Sim — casas decimais para exibição? |
| Limite alterado durante período | Usar o valor do limite no timestamp correspondente | Não (recorded já resolve) |

### 10.3 Decisões que Precisam ser Confirmadas

1. **Questionable:** Tratar como SEM_DADOS ou como o valor original?
2. **Substituted:** Incluir no cálculo ou marcar separadamente?
3. **Tolerância de alinhamento temporal:** Se leitura está em T=10:00:00 e limite em T=09:55:00, qual usar?
4. **Período mínimo:** Existe um período mínimo para considerar um "fora de limite" significativo?
5. **Intervalo de interpolação:** Para conformidade, usar recorded (preciso) ou interpolated (alinhado)?
6. **Arredondamento:** Casas decimais para exibição vs. cálculo interno com precisão total?
7. **Limite = -999:** Tratamento especial (PI AF usa como "sem dado")?

## 11. Estratégia de Persistência

### 11.1 Abordagem: Cálculo Sob Demanda com Cache

**Recomendação:** Não pré-calcular. Calcular sob demanda a cada consulta e armazenar resultados em cache + persistir para consultas futuras.

**Fluxo:**

```
1. Receber requisição de conformidade
2. Verificar se já existe resultado calculado para (equipment, period)
   → Se sim: retornar do cache/DB
   → Se não: calcular
3. Buscar dados do PI (leitura + limites) via StreamSet/recorded
4. Calcular conformidade ponto-a-ponto
5. Salvar resultado em cep_analysis_runs + cep_variable_results
6. Retornar
```

### 11.2 Por Que Não Pré-Calcular

- Períodos podem ser arbitrários (última hora, último dia, último mês)
- Limites mudam ao longo do tempo
- Pré-calcular para todos os períodos possíveis é inviável
- Cache de resultados já computados evita recálculo para períodos repetidos

### 11.3 Índices Necessários

```sql
-- cep_variables
CREATE INDEX ix_cep_variables_equipment_id ON cep_variables(equipment_id);
CREATE INDEX ix_cep_variables_section_id ON cep_variables(section_id);
CREATE INDEX ix_cep_variables_active ON cep_variables(active);

-- cep_analysis_runs
CREATE INDEX ix_cep_analysis_runs_equipment_id ON cep_analysis_runs(equipment_id);
CREATE INDEX ix_cep_analysis_runs_period ON cep_analysis_runs(start_time, end_time);

-- cep_variable_results
CREATE INDEX ix_cep_variable_results_run_id ON cep_variable_results(analysis_run_id);
CREATE INDEX ix_cep_variable_results_variable_id ON cep_variable_results(variable_id);

-- cep_out_of_limit_periods
CREATE INDEX ix_cep_out_of_limit_variable_id ON cep_out_of_limit_periods(variable_id);
CREATE INDEX ix_cep_out_of_limit_run_id ON cep_out_of_limit_periods(analysis_run_id);
CREATE INDEX ix_cep_out_of_limit_time ON cep_out_of_limit_periods(start_time, end_time);
```

### 11.4 Tratamento de Falhas

- Se o PI Web API falhar para uma tag: marcar como `SEM_DADOS` para aquela tag, continuar com as demais
- Se falhar para todas as tags: retornar erro 502 com mensagem
- Se o cálculo falhar: marcar `cep_analysis_runs.status = FAILED`, registrar `error_message`
- Rollback em caso de erro na persistência dos resultados

## 12. Riscos Técnicos

| Risco | Impacto | Probabilidade | Mitigação |
|---|---|---|---|
| PI Web API indisponível durante cálculo | Alto | Média | Retry + fallback parcial |
| Dados massivos para períodos longos | Alto | Alta | Chunking + sampling + cache |
| Alinhamento temporal impreciso | Médio | Média | Interpolated para alinhamento, ou tolerância configurável |
| Limites mudam durante o período | Médio | Baixa | Recorded já resolve (cada ponto tem seu timestamp) |
| Performance do cálculo ponto-a-ponto | Médio | Média | NumPy ou processamento em lotes |
| Concorrência de cálculos simultâneos | Baixo | Baixa | Semáforo de concorrência existente |
| Migration SQLite vs PostgreSQL futura | Baixo | Baixa | Usar render_as_batch, evitar features específicas |
| Tags sem WebId resolvido | Médio | Alta | Validar tags antes do cálculo |
